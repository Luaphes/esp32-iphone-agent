# 手机智能控制器产品提案

日期：2026 年 10 月 16 日  
状态：产品方向提案，平台实现与商业可行性待验证

面向普通消费者，提供由手机 App 和外接硬件组成的手机智能控制产品。用户购买硬件后，扫描二维码下载软件、完成必要授权和连接，即可用自然语言让云端 Agent 操作自己的手机。最终使用时不依赖另一台电脑。

当前优先验证 iPhone 控制链路，同时比较 Android 的软件方案和外接硬件方案。验证可以暂时依赖电脑，但这不改变最终希望由手机独立承载使用流程的产品目标。

## 用户提出的产品方向

- 以硬件加软件的形式提供产品，面向消费者追求开箱即用。
- iOS 和 Android 都以手机 App 作为任务入口、配置入口和运行反馈界面。
- App 调用云端 Agent，通过 ESP32 等外接设备实现对手机的操作，弥补普通 App 不能任意操纵其他 App 的限制。
- 硬件先采用插在手机 USB-C 口上的外接模块，后续探索一拖二的扩展形态，让控制模块长期连接时仍保留手机接口的使用空间。
- 硬件扩展的长期愿景是尽量保留原 USB-C 口的功能和扩展能力，成为可独立使用的手机外挂。
- 模型接入初期使用 API，倾向 DeepSeek；后期可由自有服务器统一转发模型请求。
- 当前已有 iPhone 16 Pro Max、iPhone 13 Pro Max 和一台 Android 设备可参与验证。优先使用 USB-C 的 iPhone 16 Pro Max，Lightning 机型作为后续兼容验证对象。

硬件加软件是当前产品设想；硬件定价、软件是否订阅、模型费用是否包含在售价中，尚未确定。

## 用户体验目标

建议把首轮消费者体验描述为以下流程，再通过测试判断哪些步骤能减少：

1. 购买并连接硬件，扫描包装或设备二维码进入下载与安装引导。
2. 安装手机 App，完成设备绑定、系统授权和模型连接设置。
3. 输入任务，查看 Agent 当前执行到哪一步，随时停止或手动接管。
4. 手机 App 获取画面，云端 Agent 判断下一步，硬件或系统允许的操作通道执行动作。
5. 新画面用于确认结果；任务完成、失败或需要用户处理时，给出明确反馈。

“开箱即用”是产品目标，不能等同于免除操作系统授权、iOS 签名安装或屏幕采集确认。朋友之间的免费自签测试可以验证产品价值，但不等于最终消费者的安装流程。

## 目标架构与职责

| 部件 | 目标职责 | 需要保留的边界 |
|---|---|---|
| 手机 App | 接收任务、管理连接与授权、取得屏幕信息、调用 Agent、调度动作、展示进度和停止入口 | 是用户控制入口；iOS 与 Android 的底层实现可以不同 |
| 外接控制硬件 | 向手机呈现键盘鼠标等输入设备，执行来自 App 的操作命令 | 不需要在 ESP32 上运行大模型；是否承担屏幕流中继取决于平台 |
| 云端 Agent | 根据任务与当前屏幕规划、判断动作，并检查执行结果 | 具体模型的视觉理解和坐标定位能力需要实测 |
| 后续自有服务器 | 统一接入模型服务，并按需要管理用户、用量和版本兼容 | 初期可以不建设；统一转发会新增服务成本与屏幕数据处理责任 |

目标闭环是：手机上的任务入口 → 获取当前画面 → 云端 Agent 决策 → 手机 App 下发动作 → 硬件或系统接口执行 → 再次观察画面。

“让手机操作自己”描述的是用户体验，不要求两个平台内部走完全相同的数据路径。硬件负责模拟输入，不代表它插入 USB-C 后就自动获得手机画面；屏幕采集或投屏必须有独立、可用的来源。

## 现有项目提供的基础

[esp32-iphone-agent](https://github.com/onehumanbeing/esp32-iphone-agent)主要围绕 iPhone 控制展开，目前保留两套架构：

| 版本 | 屏幕获取 | Agent 运行位置 | 硬件职责 | 当前用途 |
|---|---|---|---|---|
| legacy | iPhone 通过 AirPlay 投屏到电脑上的 UxPlay | 电脑 Python 服务 | Wi-Fi 接收命令，模拟 USB 键盘鼠标 | 先验证画面、手动控制和模型任务执行 |
| main | iPhone 投屏到 ESP32，屏幕流经蓝牙返回同一手机上的 App | iPhone App | AirPlay 中继、蓝牙通信、USB 键盘鼠标 | 更接近手机独立运行的产品形态 |

两套固件和通信协议不能混用，电脑版验证通过也不等于手机 App 版已经验证。可复用的是控制经验、模型任务用例和评测结果；迁移后仍需验证无线传输、后台运行、供电和 App 安装。[项目架构说明](https://github.com/onehumanbeing/esp32-iphone-agent/blob/main/docs/legacy.md)

2026 年 10 月 16 日的代码检查基线：main 为 `9b1a667`，legacy 为 `fc8458c`。10 月 17 日已在一块 4 MB Flash、2 MB PSRAM 的 ESP32-S3 上完成 legacy 固件刷写，并在 iPhone 16 Pro Max 上验证投屏、手动控制和 DeepSeek 短任务；重复点击与输入法兼容性仍需优化。详见 [iOS 控制验证记录](iOS控制验证记录.md)。

## USB-C 扩展形态的待验证假设

希望手机连接控制模块后仍能充电、连接其他配件，甚至保留原接口的完整能力。这应作为硬件产品目标单独验证，不能从“ESP32 能模拟键盘鼠标”直接推出。

需要分别判断充电与供电、USB 数据连接、外接键鼠和存储、音频、视频输出等能力。手机支持哪些功能、端口承担什么角色、多个外设能否同时工作，以及是否需要 USB Hub、供电协商和信号切换电路，都属于硬件设计问题。

建议首个扩展样机只承诺一个明确组合，例如“控制模块工作时仍可充电”。是否进一步支持数据配件或显示输出，依据目标手机和硬件测试决定。暂不把“完美保留原 USB-C 的全部能力”写成产品承诺。

初步资料支持将其理解为“扩展坞中集成控制模块”，而非让所有 USB 数据经过 ESP32。芯片与扩展坞资料及实验建议见 [Android 控制方案初步调研](Android控制方案初步调研.md)。

## 平台路线尚未确定

| 问题 | 当前立场 |
|---|---|
| iOS 是否需要外部硬件模拟输入 | 现有项目采用这条路线，先验证其实际效果 |
| Android 是否可以完全不用 ESP32 | 必须比较系统提供的屏幕采集、无障碍操作和开发调试通道，不能预先认定必须有硬件 |
| Android 是否采用与 iOS 相同的硬件 | 如果能明显减少授权或提升兼容性，可以考虑；不能仅为统一外形增加不必要链路 |
| 鸿蒙是否能沿用 Android 实现 | 要区分具体系统代际、应用运行环境和开放接口，不能按品牌一概判断 |
| 系统越来越封闭是否意味着外接硬件最稳定 | 是待检验假设；外接输入也无法自动解决屏幕获取、锁屏、受保护内容或供电问题 |
| 最终是否采用手机 App 版 | 产品目标倾向手机独立运行；当前先完成电脑版实验，尚未确认手机版在目标设备上的稳定性 |

Android 方案的事实和初步比较另见 [Android 控制方案初步调研](Android控制方案初步调研.md)，不将调研建议自动视为已决定的产品方向。

## 模型接入与多人使用

初期使用视觉模型 API，优先验证 DeepSeek 的图片理解、操作定位、任务完成率与成本。需要分别验证“接口支持图片”和“能可靠完成手机任务”；两者不是同一个结论。

小范围测试可以让每个参与者自行配置 API Key。密钥不写入共享固件，也不将个人密钥打包进分发软件。若后续建设统一转发服务，再确定账号、计费、限额和数据保存方式。

统一转发服务的核心是稳定的用户体验和用量管理，不必把手机的每一个实时控制步骤都迁到服务器；手机仍需处理连接、授权、执行反馈和停止。

批量刷写希望同型号硬件共用固件、每位用户单独配置设备。现有 legacy 把 Wi-Fi 和服务器地址写在固件编译配置中，正式分发前需要调整；其服务端当前一次接收一块板子，不能直接当成一台电脑管理多部手机的系统。

源码分发也属于后续交付设计的一部分：上游当前 main 明确将包含 AirPlay 移植代码的固件二进制按 GPL 3.0 分发，其余部分主要为 MIT。采用该版本制作商业硬件时，应按实际采用的代码确定源码与许可证交付方式。[上游许可说明](https://github.com/onehumanbeing/esp32-iphone-agent#license)

## 下一步验证与验收

1. **iOS 基础闭环**：使用一块 ESP32-S3 和 iPhone 16 Pro Max，在电脑上看到实时画面，能够手动点击、滑动、输入英文或数字，并校准位置。退出或断开后不继续操作。
2. **云端 Agent 任务**：接入 DeepSeek，使用“打开设置”和“设置指定闹钟”等可检查结果的短任务，记录成功率、耗时、模型费用和人工接管次数。现有键盘通道只支持 ASCII，中文输入另行验证。
3. **Android 路线比较**：在已有 Android 设备上比较不带硬件的系统接口方案与外接 HID 方案。先比较屏幕获取、点按输入、授权步骤、重启恢复和后台稳定性，再决定是否保留 ESP32。
4. **手机独立运行**：在明确选定的平台路线后，验证离开电脑的完整任务闭环。iOS 还需检查 App 签名、配网、蓝牙视频传输及后台运行。
5. **消费者交付**：验证一个未参与开发的人能否完成安装、首次配置、首个任务和故障恢复，再讨论批量生产、USB-C 扩展设计与商业分发。

首轮验收以真实设备上的完整任务和新用户设置体验为依据。单元测试通过、模型接口返回成功、鼠标能移动，都只是其中一部分。

## 需要共同决定的事项

- 第一批用户最希望完成的手机任务，以及能接受的等待时间和人工接管频率。
- 是否必须同时覆盖 iOS 与 Android，还是先选一个平台完成消费级体验。
- 外接硬件的必要价值是跨系统输入、充电扩展、降低配置成本，还是其他能力。
- USB-C 扩展首版究竟支持哪些功能，哪些明确留到后续。
- 用户自行提供模型 API，还是购买后直接使用统一服务；软件收费方式如何确定。
- 免费自签、TestFlight 或正式应用分发分别承担哪个阶段的交付。
