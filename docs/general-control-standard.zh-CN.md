# 通用设备控制能力：判断、修复与验收标准

日期：2026-10-17。本文作为后续本地修复的判断与验收依据。原则已经确认；下面的目标标准不代表当前程序已经实现或通过验收。

## 1. 目标与范围

目标是让同一套控制机制可靠处理不同应用、设备及横竖屏：根据实际画面理解目标、执行动作、验证效果，遇到不确定性能够恢复或如实停止。

- 不将某个应用的固定坐标、按钮顺序、预设成功答案写入通用控制层。
- 笑脸、搜索、闹钟等可以作为回归用例，不能成为修复成立的唯一证明。
- 用户任务可以包含业务步骤；为排查临时提供的按钮提示只能算辅助实验，不能算通用能力已经修好。
- 主闭环继续以 DS 实测；Codex 用于代码与必要诊断。人工或其他模型接管后的成功，不计为 DS 自主完成。DS 用量可增加，本机 Codex 用量应控制。

## 2. 当前架构与提示词（已核对事实）

本节描述上游 `legacy` 的 `fc8458c39d769b4a48d500fc6d53574bd7b77e9e`，不是对上游其他分支或最新主线的结论。核对时 Planner、Actor 的配置名称均为 `deepseek-flash`；角色可分别配置模型。

```text
用户目标 + 当前截图
        ↓
Planner：规划提示词 → 最多 6 步计划
        ↓
Actor：执行提示词 + 目标 + 计划 + 最近动作记录 + 当前截图
        ↓
THINK / DO 文本 → Python 解析与调度 → Phone 指针控制 → ESP32 HID
        ↓
设备画面 → AirPlay 截图 → 画面变化标记及最近记录 → 下一轮 Actor
```

| 组成 | 当前内容与职责 | 来源 |
| --- | --- | --- |
| 规划系统提示词 | 从当前画面制定短计划；不要编造未见页面；优先通过搜索打开应用 | [PLANNER_PROMPT](../server/hidagent/agent.py) |
| 执行系统提示词 | 0–1000 截图坐标、动作语法、单步/批量规则、查看上一步效果、精确点击、重规划、done/fail | [ACTOR_PROMPT](../server/hidagent/agent.py) |
| 动态上下文 | 每轮传入目标、计划、最近 8 条事件中的动作及变化标记、当前截图；卡住或解析失败时有补充提醒 | `_next_actions`、`_replan` |
| API 消息 | 每次调用通常为一条 system 和一条包含文本、截图的 user 消息；没有自动传入全部聊天历史 | [LLM.chat](../server/hidagent/llm.py) |
| 程序执行 | 解析 DO、调度动作、坐标换算、串行 HID 指令、重试和步数限制 | [Agent](../server/hidagent/agent.py)、[Phone](../server/hidagent/phone.py) |
| 简单视觉反馈 | 指针差分定位，以及画面 changed / not changed | [vision.py](../server/hidagent/vision.py) |

两个角色目前使用相同模型名称，但不是两个能自动共享全部记忆的常驻会话。每轮输入由 Python 重新组装；本地文档、Codex 对话及临时诊断经验不会自动变成 DS 的长期提示词。

当前固定提示词称设备为 iPhone；已要求模型根据截图行动，并非写死一套 iPhone 按钮坐标。仅替换“iPhone”为“iPad”不能被视为问题已解决。

**提示词约束与程序保证必须区分。** 当前没有独立的任务完成验证环节；同一 Actor 可以输出 done，程序会直接结案。它可以在一批中返回最多 6 个动作，这些动作共用决策前截图。

## 3. 根因判断：分层归因，避免将症状当根因

当前系统允许错误理解、未确认落点、未经证实的效果继续向下传播。DS 的视觉误判是实际因素，系统未能发现和恢复这些误判是控制架构的缺口；不能只归因于模型，也不能声称模型错误能够被程序完全消除。

| 层次 | 已确认的缺口 | 修复方向 |
| --- | --- | --- |
| 感知与定位 | 会认错图标、页面和工具状态；目标含义与坐标之间缺少可靠复核 | 以当前截图定位，必要时局部观察；区分设备当前页面与预期页面 |
| 指针与动作 | 普通点击不一定定位指针；精确点击定位失败仍可能继续，修正一次后不确认最终落点 | 使关键动作建立在可核验的实际落点上，校准结果必须经过实际落点验收 |
| 状态与进展 | 画面变化可能来自指针、悬停提示、通知中心或无关滚动 | 分别记录指令已发送、画面有变化、预期效果已确认 |
| 完成判定 | 允许在产生结果的同一批动作里 done，没有读取结果产生后的新截图 | 用执行后的新证据核对目标，再结案 |
| 恢复策略 | 类似动作因持续产生变化而未触发有效重规划 | 基于目标状态是否推进识别循环，进行有限且有依据的恢复 |

上游演示、README 描述、单元测试通过，不等同于当前“模型＋iPad 系统＋屏幕方向＋固件”组合已通过真机验证。当前板上保留此前的兼容扩展固件，不能将现状描述成完整软硬件都与上游逐字一致。

## 4. 通用修复的必要标准（目标状态）

### 看对：目标必须与实际画面对应

- 目标应能说明要操作什么、位于当前画面的哪个区域，以及动作需要什么前置状态；坐标取自该截图。
- 必须区分应用画布、工具栏、键盘、通知中心、控制中心等状态。出现系统覆盖层时，先恢复并重新观察。
- 屏幕方向、尺寸或比例变化后重新验证坐标映射；不能沿用失效的校准或此前布局。
- 不确定目标时可以局部放大、重新观察、尝试可验证的替代入口；不能将任务描述中的预期当成已观测事实。

### 点准：执行结果必须可核验

- 关键、小目标点击要核实实际指针落点，再按下；修正后的落点仍需确认。容差依据目标有效区域与大小，不能机械地要求所有目标达到同一个极小像素误差。
- 指针探测失败意味着“缺少定位证据”，不自动等于动作失败。应先考虑等待新帧、换一种探测或可验证的替代操作；仍无法确认时，不得继续盲点或误报成功。
- 归零、校准与恢复不能默认无副作用；若触发系统页面，需要恢复并重建对当前状态的认识。
- 路径、拖动和滑动分别验证起点、方向、终点与应用效果；仅串口/Wi-Fi 返回 ok 不代表手势已经生效。

### 验证效果：每个依赖状态的动作之后重新观察

- 后续动作依赖打开菜单、进入页面、聚焦输入框、启用工具的结果时，先取得执行后的截图并确认前置条件。
- 只对不依赖中间观察的动作使用批量执行。批量绘图也必须先确认绘图模式确实生效。
- 按动作的预期效果判断进展：例如菜单出现、应用打开、内容保存、画布出现墨迹。画面变化本身不是成功证据。
- 证据不足时保留未确认状态；不能通过不断追加提示词，将未确认包装成已完成。

### 完成与恢复：有证据才结案

- 完成判定必须使用所有相关动作完成后的新截图或其他直接状态证据；不得与产生结果的动作共用旧截图直接 done。
- 按用户目标逐项核对，区分完成、部分完成、失败和无法验证。同一个 DS 可以承担复核，但另一次调用本身不保证判断独立或正确。
- 连续没有推进目标状态时，恢复必须有新依据，例如目标位置、页面判断或执行方式发生修正；无意义地修改几像素不算新策略。
- 到达恢复预算或无法观察时如实停止，记录缺少什么证据；不能以步数用尽代替原因诊断。

以上按职责划分要求，不预设必须增加多个模型、服务或复杂编排；优先补齐现有闭环的最小缺口。

## 5. 验收与回归标准

先验证指针与手势，再验证状态识别、动作串联、最终完成判断。底层未通过时，不靠增加任务专用提示掩盖问题。

| 能力 | 最小覆盖方向 | 必须保留的证据 |
| --- | --- | --- |
| 定位 | 屏幕中央、四周、大小目标；不同背景 | 目标区域、实际落点、偏差、最终是否确认 |
| 手势 | 上下/左右滚动、拖动；边缘动作与普通动作 | 起止状态、实际效果、是否误开系统覆盖层 |
| 交互链 | 至少两个不同应用，覆盖打开工具、输入、状态切换；内容改动使用明确授权的测试数据 | 每一步前置条件和执行后证据 |
| 布局变化 | iPad 横竖屏；若宣称支持 iPhone，需加入真实 iPhone | 分设备/方向的结果；不能从一个设备外推另一个 |
| 故障恢复 | 未命中、指针不可见、错误页面、界面未变、系统覆盖层 | 能恢复或如实停止，无盲目循环 |
| 完成判断 | 明确成功、完全无效、部分完成三类 | 不得将后两类报告成成功；复核使用执行后新证据 |

- 对每种条件记录成功次数/总次数、误报成功次数、人工接管、恢复次数与耗时。试验前明确重复次数，不能只展示一次成功；任何误报完成均判该轮验收不通过。
- 人工指路、手动点击、其他模型代替识别的运行单独标记。辅助成功与自主成功不能合并统计。
- 记录源码提交、提示词版本、模型配置名称、固件、设备/系统与方向、校准状态、任务、截图/时间、动作、验证结论；不得收录凭证或无关个人内容。
- 新机制需保留上游基线和此前修改版，先小范围验证，再扩大回归。只完成文档、单元测试或服务启动，不得宣称真机能力已修复。
